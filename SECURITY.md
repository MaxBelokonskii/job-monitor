# Модель безопасности Job Monitor

Job Monitor — локальный инструмент: сервер слушает только `127.0.0.1`, интерфейс
открывается в браузере на той же машине. Этот документ фиксирует, от чего
приложение защищается, где живут секреты, какими механизмами это обеспечено и
что делать, если секрет всё-таки утёк. Он описывает текущее состояние кода
после плана `2026-09-08-security-hardening`, а не то, что запланировано на
будущее.

## Модель угроз

**От чего защищаемся:**

- **Враждебная веб-страница в том же браузере.** Пользователь может держать
  открытыми другие вкладки, пока работает Job Monitor. Без защиты такая
  страница могла бы дёрнуть локальный API (CSRF) или обратиться к нему через
  DNS rebinding, притворившись легитимным доменом, который резолвится в
  `127.0.0.1`.
- **Недоверенный контент из Telegram и hh.ru.** Тексты вакансий, имена
  каналов и сообщения контактов приходят от третьих лиц и отображаются в
  интерфейсе. Это классический источник XSS, если рендерить их как HTML.
- **Утечка секретов через git.** Исходный инцидент, из-за которого возник
  этот план: архив с `.env`, живыми Telethon `.session`-файлами, логами
  контактов и резюме был закоммичен в публичный репозиторий, потому что
  `.gitignore` не видит содержимое `.rar`.

**От чего не защищаемся (осознанно, вне области):**

- Локальный пользователь с доступом к домашнему каталогу (`~`). Если у
  атакующего уже есть выполнение кода под учётной записью пользователя, игра
  окончена — он может прочитать `.env` напрямую, независимо от прав доступа.
- Физический доступ к машине.
- Многопользовательская среда — приложение не проектировалось для запуска
  на сервере, к которому обращаются разные люди.

## Где лежат секреты

Всё состояние приложения — секреты, конфигурация, сессии, логи — живёт вне
репозитория, под `$JOB_MONITOR_DATA_DIR`. Если переменная не задана,
используется `~/.job-monitor`. Единственное место, где вычисляется этот путь —
`job_monitor/paths.py`.

Каталог создаётся с правами `0700` (`data_dir()` в `job_monitor/paths.py`), а
если каталог уже существовал и был доступен группе или всем — права
приводятся к `0700` при следующем обращении. Правятся они только в сторону
ужесточения: `paths.tighten()` снимает биты доступа и никогда не добавляет
новых, так что каталог, который пользователь сделал строже (`0500`), таким и
останется. Причина — каталог мог достаться от версии, которая ещё не ставила
режим, или быть распакован из архива: `tar` сохраняет права как есть.

**Ужесточение прав — best-effort.** Если `chmod` на этом томе запрещён
(exFAT/SMB/NFS — `JOB_MONITOR_DATA_DIR` вполне может указывать на флешку;
файл, доставшийся другому владельцу после однократного запуска под `sudo`;
иммутабельный флаг), приложение продолжает работать, а отказ пишет в лог —
один раз на файл, с именем файла и без полного пути. Иначе получалось хуже:
`tighten()` зовётся из `data_dir()`, а тот — из `configure_logging()` в
`lifespan`, и отказ `chmod` не давал серверу подняться вообще. Практический
вывод для такого тома: **режим файла там не защищает ничего**, и каталог
данных надо защищать средствами тома или не держать его там.

Каждый файл состояния — `0600`:

| файл | кто ставит права |
|------|------------------|
| `.env` | `job_monitor/envfile.py::write_env` — атомарно: временный файл рядом, `chmod`, `os.replace` |
| `job_monitor.db` и её спутники `-wal`, `-shm` | `job_monitor/db/connection.py::connect` |
| `telegram.session` (и `-journal`) | `job_monitor/telegram_client.py::get_client` |
| `hh_cookies.json` | `job_monitor/workers/hh.py::save_cookies` |
| `logs/*.log` | `job_monitor/logging_setup.py::PrivateRotatingFileHandler` |

База и файл сессии до финальной волны создавались по umask, то есть обычно
`0644`, и защищались только режимом каталога. Под моделью угроз D1 (локальный
однопользовательский инструмент) это не дыра, но асимметрия с остальными
файлами ничем не оправдана: в `telegram.session` лежит `auth_key`, которого
достаточно для входа в аккаунт в обход 2FA, а в базе — переписка и контакты.
`-wal` считается наравне с базой: пока данные не перенесены в неё, они лежат
именно там.

Сегодня в каталоге данных фактически лежат:

- `job_monitor.db` — SQLite и единственный источник правды: настройки, а также
  таблицы контактов (`tg_contacts`/`tg_sends`) и вакансий
  (`hh_applications`), которые теперь наполняют сами воркеры —
  **это значит, что база хранит имена всех, кому когда-либо писали, и всю
  историю вакансий**, и именно её нужно учитывать при реакции на утечку
  наравне с файлами ниже;
- `.env` — только `TG_API_ID` и `TG_API_HASH`, и ничего больше. Прикладные
  настройки (`safe_mode`, `parse_history`, `history_limit` и остальные) живут
  в `job_monitor.db` и правятся через UI: правка их в `.env` ни на что не
  влияет. Раньше приложение дописывало сюда их копию, которую никто не читал,
  и `SAFE_MODE=true`, выставленный руками, создавал ложное ощущение
  безопасного режима, пока воркер продолжал рассылать сообщения. Файл ваш, и
  приложение обращается с ним соответственно: комментарии, пустые строки и
  порядок строк сохраняются при записи, значение известного ключа
  переписывается на своём месте. Строку, которую не удалось разобрать (нет
  имени переменной или нет `=`), чтение пропускает и один раз сообщает о ней
  в лог — с номером строки, но без содержимого, потому что в `.env` лежат
  секреты. Символы `\n`, `\r`, `\x00` — исключение: на них чтение
  останавливается с ошибкой, потому что руками такое не набирают, а
  переменной такое значение не порождает ни при чтении, ни при записи;
- `telegram.session` — живая сессия Telethon, одна на всё приложение: и
  воркер, и просмотр переписки в UI работают через один клиент
  (`job_monitor/telegram_client.py`);
- `hh_cookies.json` — cookies сессии hh.ru;
- `logs/tg_system.log`, `logs/hh.log` — логи TG- и HH-стороны, те же, что
  показывают вкладки логов в UI. Пишет их `job_monitor/logging_setup.py`:
  права `0600`, ротация по размеру. В логи попадают тексты постов из Telegram
  и заголовки вакансий с hh.ru — то есть содержимое, но не секреты: ни
  `TG_API_HASH`, ни `TG_API_ID`, ни cookies, ни содержимое сессий в лог не
  пишутся.

Чего в каталоге данных больше не должно быть — но может лежать как след
предыдущих версий:

- `telegram_web.session` — **второй файл сессии Telethon, больше не
  используется.** До версии `2.1.0` веб-часть входила в Telegram отдельно от
  монитора, то есть в один аккаунт было два независимых логина (дефект L8);
  сейчас клиент один. Приложение этот файл не читает, не пишет и намеренно не
  удаляет — состояние в каталоге данных принадлежит вам. **Удалите его
  вручную:** файл сессии Telethon содержит `auth_key`, и его одного
  достаточно, чтобы войти в аккаунт — без пароля и в обход 2FA. Лежащий без
  дела он не даёт ничего, кроме второго экземпляра самого опасного секрета в
  этом каталоге.
- `hh_sent.json`, `all_sent_users.txt`, `logs/sent_log_*.txt` — старые
  файловые списки обработанных вакансий и контактов. Их роль перешла к
  таблицам в `job_monitor.db`, ни один воркер их больше не читает и не пишет.
  Удалять можно после того, как убедились, что `migrate-legacy` перенёс
  данные (они видны в UI): повторно импортировать будет уже неоткуда.
- `config.json` — не используется: до плана `storage-foundation` здесь
  хранились несекретные настройки, но их больше не читает ни один код.
- `monitor_pid.txt`, `hh_pid.txt` — PID-файлы отдельных процессов-мониторов.
  Процессов больше нет, воркеры живут внутри приложения
  (`docs/adr/0001-in-process-workers.md`), файлы никем не читаются.

В репозитории состояния нет и быть не должно: `.gitignore` перечисляет каждое
из этих имён, и pre-commit хук (`scripts/check_no_secrets.py`) отдельно
проверяет и имя, и первые байты каждого коммитимого файла — на случай, если
кто-то переименует секрет или спрячет его в архиве.

## Механизмы

- **`X-App-Token` на каждый `/api/*` запрос.** При старте процесса
  `job_monitor/security.py` генерирует случайный `APP_TOKEN =
  secrets.token_urlsafe(32)`. Middleware `app_token_middleware` сверяет
  заголовок `X-App-Token` с этим значением через `secrets.compare_digest` и
  отвечает `403`, если токена нет или он не совпал. Токен живёт только в
  памяти процесса и подставляется в отдаваемый HTML на лету: `serve_ui()` в
  `api/main.py` читает `frontend/index.html` и заменяет плейсхолдер
  `__APP_TOKEN__` на реальное значение перед отправкой ответа; на диске
  `index.html` плейсхолдер и держит. Это закрывает CSRF — сторонняя страница
  не может узнать токен и не может заставить браузер отправить его сама
  (в отличие от cookie, который браузер приложил бы автоматически).
- **`TrustedHostMiddleware` на `127.0.0.1` и `localhost`.** Настроен в
  `job_monitor/security.py` (`ALLOWED_HOSTS = ["127.0.0.1", "localhost"]`).
  В `api/main.py` он зарегистрирован после `app_token_middleware` по коду —
  но у Starlette middleware, добавленный позже, оборачивает предыдущие
  снаружи и поэтому видит запрос раньше их. Из трёх middleware в
  `api/main.py` (`app_token_middleware`, `TrustedHostMiddleware`,
  `security_headers_middleware`, в порядке регистрации) фактический порядок
  выполнения на входящий запрос — обратный: `security_headers_middleware`,
  затем `TrustedHostMiddleware`, затем `app_token_middleware`.
  Значит запрос с чужим `Host` получает `400` от `TrustedHostMiddleware` до
  того, как дело доходит до проверки токена. Это защита от DNS rebinding:
  даже если вредоносный домен резолвится в `127.0.0.1`, запрос с таким
  `Host` заголовком будет отвергнут.
- **Почему `GET /` не под токеном, и от чего это зависит.** Корневая
  страница отдаёт токен внутри HTML, поэтому сама она защищена быть им не
  может — иначе его негде было бы взять. Безопасность этой схемы держится
  ровно на двух условиях, и оба обязательны:

  1. `TrustedHostMiddleware` отвергает запрос с чужим `Host` — значит
     вредоносный домен, резолвящийся в `127.0.0.1`, страницу не получит
     (DNS rebinding);
  2. браузерная политика одного источника не даёт скрипту на чужой
     странице прочитать тело ответа с `127.0.0.1:8000`. Это условие даёт
     сам браузер, а не мы, — и приложение больше **ничем его не
     ослабляет**.

  Второй пункт раньше звучал иначе: «allow-лист CORS не даёт чужому
  `Origin` прочитать ответ». `CORSMiddleware` из `api/main.py` убран
  целиком, и это строго строже, чем был allow-лист. Почему:

  * ни один запрос UI не был кросс-доменным — страница отдаётся с того же
    адреса, куда стучится относительными путями (`const API = '/api'` в
    `frontend/app.js`), — то есть allow-лист ничего приложению не
    *разрешал*;
  * зато он был единственным местом, где разрешение вообще выдаётся.
    Отсутствие middleware означает, что `Access-Control-Allow-Origin` не
    отдаётся НИКОГДА и ни одному источнику; с allow-листом браузер
    отказывает всем, кроме перечисленных, а без него — всем.

  Цена ошибки в этой строке была высока именно из-за `GET /`: мутационный
  аудит показал, что расширение до `allow_origins=["*"]` проходило при
  полностью зелёном наборе тестов, а токен со `/` достаётся тогда первому
  же открытому в браузере сайту — а с токеном идут чтение переписки в
  Telegram, отправка сообщений от лица пользователя и выгрузка контактов.
  Убрав middleware, мы убрали и саму возможность такой мутации. Оба
  условия закреплены: `tests/test_no_cross_origin_permission.py` требует,
  чтобы `Access-Control-*` не было ни в одном ответе ни одному источнику —
  включая собственный (иначе возврат «безопасного» allow-листа из двух
  loopback-адресов остался бы незамеченным), — и чтобы middleware не
  вернулся в стек; `tests/test_route_invariants.py` сторожит, что вне
  `/api/` нет ничего, кроме `/` и `/static`.
- **CSP и заголовки ответа.** `job_monitor/security.py` определяет `CSP` и
  `SECURITY_HEADERS` (`Content-Security-Policy`, `X-Content-Type-Options:
  nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`),
  применяемые в `security_headers_middleware` ко всем ответам. `script-src`
  — `'self'`, без `'unsafe-inline'`: все тридцать инлайновых `on*=`
  обработчиков убраны из `frontend/index.html` и заменены делегированной
  картой `ACTIONS` по атрибутам `data-action`. Инвариант закреплён с двух
  сторон: `tests/test_frontend_events.py` падает, если в разметке появится
  хотя бы один инлайновый обработчик, а `tests/test_frontend_safety.py` —
  если `'unsafe-inline'` вернётся в `script-src`. `style-src` сохраняет
  `'unsafe-inline'` осознанно: атрибуты `style` в разметке — не вектор
  исполнения кода.
- **Запрет `innerHTML` в `app.js`.** Весь недоверенный контент из Telegram и
  hh.ru рендерится через `el()`/`fill()` — построение DOM-узлов и
  `textContent`, а не сборку HTML-строк. Инвариант «в `app.js` нет
  `innerHTML`» закреплён тестом `tests/test_frontend_safety.py::
  test_app_js_never_uses_inner_html`, который падает, если подстрока
  `innerHTML` появится в файле. Отдельно, ссылки на вакансии hh.ru проходят
  через `isHttpUrl()` — allowlist схем `http`/`https` — прежде чем попасть в
  атрибут `href`, что закрывает инъекцию через `javascript:`-ссылку
  (проверено тестом `test_hh_vacancy_url_scheme_guard_rejects_script_schemes`).
- **Pre-commit `scripts/check_no_secrets.py`.** Локальный хук в
  `.pre-commit-config.yaml`, идущий перед пиновым хуком
  `Yelp/detect-secrets`. Отклоняет коммит, если среди файлов есть запрещённое
  имя (`.env`, `*.session`, `config.json`, `*cookies*.json` и т. д. — полный
  список в `FORBIDDEN_NAMES` в самом скрипте) или файл, чьи первые байты
  совпадают с сигнатурой архива (RAR, ZIP, 7z, GZIP) — именно так утекли
  секреты в исходном инциденте, и именно поэтому проверка смотрит внутрь
  файла, а не только на имя.

## Что делать при утечке

Порядок важен: сначала действия, без которых остальные бессмысленны.

1. **Telegram → Настройки → Устройства → завершить все сеансы.** Это
   немедленно обнуляет `auth_key` скомпрометированной сессии. Пока сессия
   жива, у атакующего есть полный доступ к аккаунту (чтение сообщений,
   отправка от вашего имени), и любые последующие шаги ничего не изменят —
   поэтому это всегда первый шаг, а не последний.
2. **Перевыпустить `api_hash`** на https://my.telegram.org/apps. Старый
   `api_hash` в паре со старым `api_id` больше не должен работать.
3. **Вычистить файл из истории git**: `git filter-repo --path <файл>
   --invert-paths`, затем force-push. Обычный `git rm` из истории коммит не
   удаляет — файл остаётся достижим через старые коммиты и форки.
4. **Попросить GitHub очистить кэш** (кэш репозитория и, при необходимости,
   кэш форков/PR) — после force-push старые blob'ы могут оставаться
   доступными через закешированные ссылки некоторое время.
5. **Уведомить людей, чьи данные были в утечке** — контакты, чьи сообщения
   или резюме попали в утёкшие логи, `all_sent_users.txt`/`sent_log_*.txt`
   или таблицы `tg_contacts`/`tg_sends`/`hh_applications` в
   `job_monitor.db`, вправе знать об этом.

## Чего никогда не делать

- Коммитить архивы проекта (`.rar`, `.zip`, `.7z`, `.tar*`) — `.gitignore`
  не видит их содержимое, а именно так секреты утекли в прошлый раз.
- Отдавать секрет через API ни в каком виде — ни как значение, ни как
  хеш/маску, которые можно спутать со значением. (`GET /api/config` отдаёт
  только `api_hash_set: bool`, никогда сам `api_hash`; эндпоинт
  `/api/config/reveal-hash` удалён.)
- Ставить пакеты в рантайме (`pip install` из кода приложения). Установка
  зависимостей — исключительно на этапе `make install` / `start_web.bat`, до
  запуска сервера.
- Слушать адрес, отличный от `127.0.0.1`. Job Monitor — локальный инструмент;
  бинд на `0.0.0.0` или внешний интерфейс выводит незащищённый (кроме
  `X-App-Token`) API в сеть.
