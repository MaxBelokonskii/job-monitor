# ADR 0001: воркеры внутри процесса приложения

**Дата:** 2026-09-08
**Статус:** принято (план 3, `docs/superpowers/plans/2026-09-08-workers-and-logic.md`)

## Контекст

До этого решения TG- и HH-мониторы были отдельными скриптами (`monitor.py`,
`hh_monitor.py`), которые API запускал через `subprocess.Popen`, а отслеживал
через PID-файлы в каталоге данных (`monitor_pid.txt`, `hh_pid.txt`). Метрики
для дашборда вычислялись парсингом текста логов: «сколько строк», «сколько раз
встретилось `[ВАКАНСИЯ]`».

Что с этим было не так — по пунктам инвентаря дефектов
(`docs/superpowers/specs/2026-09-08-hardening-and-rework-spec.md`):

- **L3.** `hh_is_running()` читал `hh_pid.txt`, но `hh_monitor.py` этот файл
  никогда не писал. После перезапуска API живой монитор был для него невидим,
  а автозапуск поднимал второй Chrome поверх работающего первого.
- **L2.** `monitor.py` обрезал лог до 5000 строк, а счётчики считались из этого
  же текста — метрики врали тем сильнее, чем дольше работал монитор.
- **L4.** `_manual_login()` в HH-скрипте блокировался на `input()`. Запущенный
  из UI через `Popen` без stdin, он не работал вообще: сценарий hh.ru был
  недостижим из интерфейса.
- Крах подпроцесса не оставлял следов, кроме протухшего PID-файла: причина
  падения жила в его stderr, которого никто не читал.

## Решение

Воркеры переехали внутрь процесса FastAPI как asyncio-таски под супервизором
`job_monitor/workers/manager.py::WorkerManager`.

- `WorkerManager` регистрирует фабрики воркеров, стартует их через
  `asyncio.create_task(self._supervise(name))`, останавливает через
  `task.cancel()` и хранит `WorkerStatus` (состояние, время старта, последняя
  ошибка) в памяти.
- Ни PID-файлов, ни `subprocess`. Единственный источник правды о том, работает
  ли воркер, — таска, которой владеет тот же процесс, что отвечает на
  `GET /api/state`.
- Метрики считаются из SQLite (`TgRepo`, `HhRepo`, `EventsRepo`), а не из
  текста логов. Логи снова стали только логами.
- Вход в hh.ru — неблокирующая машина состояний `HhLogin` вместо `input()`:
  UI жмёт «Начать вход», открывается браузер, пользователь входит руками,
  UI жмёт «Я вошёл»; состояние входа приходит в общем `GET /api/state` (`hh.login_state`) вместе со всем остальным, что рисует дашборд.

## Последствия

**Хорошее.**

- Падение воркера не роняет API: `_supervise` ловит любое исключение, пишет
  трассировку в лог этого воркера и переводит статус в `error` с текстом
  ошибки, который виден в UI. Приложение продолжает отвечать.
- Одна сессия Telethon на всё приложение (`job_monitor/telegram_client.py`) —
  раньше монитор и веб-чат держали два независимых логина в один аккаунт (L8).
- Статус, метрики и история — из одного места, и они согласованы между собой.

**Цена, которую мы приняли.**

- **Selenium требует отдельного потока.** Драйвер синхронный и блокирующий,
  поэтому HH-воркер оборачивает его в `asyncio.to_thread`. Поток нельзя
  отменить: `task.cancel()` до него не доходит. Остановка кооперативная —
  воркер выставляет `threading.Event`, а цикл Selenium проверяет его между
  шагами и выходит сам.
- **У остановки есть бюджет времени.** `WorkerManager.stop()` ждёт таску
  ограниченное время (`asyncio.wait`, а не `wait_for` — тот после своего
  дедлайна ждёт завершения уже без ограничения). Если воркер не уложился,
  статус становится `error`, таска остаётся под наблюдением, и следующий
  `start()` откажет с 400. Воркер в этом состоянии не перезапустить без
  перезапуска процесса — это осознанно меньшее зло, чем соврать «остановлен» и
  дать пользователю поднять второй экземпляр поверх живого. `POST /api/tg/stop`
  и `POST /api/hh/stop` возвращают настоящее состояние, а не безусловное
  `stopped`.
- **У каждого запуска есть номер (`epoch`), и ответ на остановку помечен
  своим.** Сторож остановки живёт отдельной таской и переживает отмену
  ожидающего; проснувшись, он молчит, если таской уже владеет другой запуск,
  — и тогда возвращает текущее состояние. Клиент, чья остановка попала в это
  окно, получал живое `running` и не мог отличить «мою остановку отменили»
  от «воркер уже перезапустили без меня»: в ответе не было ни слова о том, к
  какому запуску он относится. `WorkerManager` поэтому держит монотонный
  счётчик запусков на воркера (`_epoch`, увеличивается на каждом успешном
  `start()`), `stop()` запоминает его на входе и возвращает вместе со
  статусом, а `POST /start`, `POST /stop` и `GET /api/state` несут `epoch`
  наружу. `frontend/app.js` помнит последний известный номер и **игнорирует
  ответ на остановку с меньшим** — не перерисовывает по нему состояние и не
  показывает тост; свежее состояние придёт следующим тиком опроса.
  Счётчик живёт только в памяти процесса — как и сам реестр воркеров, — и
  это осознанно: после перезапуска процесса нет ни одной таски и ни одного
  ожидающего ответа, чей номер было бы с чем сравнивать.
- **Несколько экземпляров приложения одновременно запускать нельзя.** БД одна,
  файл сессии Telethon один, cookies hh.ru одни. Второй процесс на том же
  `$JOB_MONITOR_DATA_DIR` — это конкурирующая запись в SQLite и два клиента на
  одну сессию Telegram. Нужны параллельные профили — задавайте разные
  `JOB_MONITOR_DATA_DIR`.
- **Тяжёлый воркер делит event loop с API.** Пока это приемлемо: TG-воркер
  ждёт события Telethon, HH-воркер живёт в отдельном потоке, а API обслуживает
  одного пользователя на localhost.

## Что стало со старыми точками входа

`monitor.py` и `hh_monitor.py` удалены (задача 7 плана 3). Их логика живёт в
`job_monitor/workers/telegram.py`, `job_monitor/workers/hh.py` и
`job_monitor/workers/hh_steps.py`. Вместе с ними исчезли и файловые «хранилища»
дедупликации (`all_sent_users.txt`, `hh_sent.json`) — их роль взяли таблицы
SQLite. Файлы логов остались файлами: их пишет `job_monitor/logging_setup.py`,
подключая обработчики в `lifespan`, и отдают `GET /api/tg/logs` и
`GET /api/hh/logs`.
