# Job Monitor: пресеты поиска и библиотека резюме

**Дата:** 2026-09-09
**Статус:** принята
**Подпроект:** 1 из 3 продуктовой переработки
**Предшествующая спецификация:** `2026-09-08-hardening-and-rework-spec.md` (укрепление безопасности и архитектуры, закрыта)

## 1. Зачем это

Приложение унаследовано и умеет искать работу — но только ту, которую искал предыдущий
автор. Значения по умолчанию в `job_monitor/settings.py` это буквально чужой поиск:

- каналы `itvacancykz`, `it_interns`, `jobfortester`, `workitkz`, `qajoboffer`, `jobforqa`;
- ключевые слова `qa`, `тестировщик`, `manual qa`, `junior`, `стажер`, `стажировка`,
  `intern`, `trainee`, `без опыта`;
- стоп-слова `senior`, `lead`, `middle`, `middle 3+`, `middle+`, `5+ лет`, `6+ лет`;
- hh.ru: запросы `QA`, `тестировщик`, `Junior QA`, `стажировка QA`, опыт `noExperience`.

То есть из коробки это «джуниор-тестировщик без опыта», зашитый в код. Владелец
репозитория ищет другое, а через месяц — возможно, третье. Приложение должно уметь
хранить несколько наборов критериев и переключаться между ними одним нажатием.

Второй разрыв: выбор файла резюме — мёртвая функция. `onFileSelect` в
`frontend/app.js` обновляет три подписи в интерфейсе и никогда не отправляет
`file_path` на бэкенд (дефект L14 предыдущей спецификации, единственный оставленный
открытым). Значит резюме к отклику приложить нельзя вообще.

## 2. Область подпроекта

Продуктовая переработка разбита на три подпроекта, каждый со своей спецификацией,
планом и циклом реализации. Порядок обусловлен зависимостями: интерфейс рисуется под
готовую модель данных, а не под движущуюся.

1. **Этот подпроект.** Модель данных: пресеты критериев, библиотека резюме, снятие
   хардкода, таблица найденного в Telegram (на запись). Плюс минимальная адаптация
   существующего интерфейса, чтобы приложение осталось работоспособным.
2. **Очередь найденных вакансий.** Список найденного со ссылками, ручной отклик,
   ручная простановка статуса, взаимодействие ручных статусов с автоматической
   дедупликацией.
3. **Переработка UI/UX.** Интерфейс целиком, поверх устоявшегося API.

**Вне области этого подпроекта:** статусы и очередь (подпроект 2); редизайн
(подпроект 3); экспорт и импорт пресетов; справочники hh.ru из официального API
(не нужны — см. D8); мультипользовательский режим, HTTPS и доступ извне (вне области
всего продукта).

## 3. Принятые решения

- **D7 — состав пресета: только критерии поиска.** В пресете лежит то, что описывает
  *что* человек ищет. Лимиты в сутки, задержки между отправками, безопасный режим,
  автозапуск и история отправок — глобальные. Причина не в удобстве: лимит существует
  потому, что банят **аккаунт**, а не пресет. Три пресета по 25 отправок дали бы 75
  сообщений в сутки с одного аккаунта — прямой путь к бану.
- **D8 — регион и словари hh.ru: константы, не настройки.** Поиск ведётся только по
  региону `113`. Занятость, опыт и график — предопределённые наборы значений hh.ru, из
  которых интерфейс строит переключатели. Следствие: официальное API hh.ru не нужно
  даже для справочников.
- **D9 — переключение пресета останавливает воркеров.** Горячая замена на ходу
  отвергнута: воркер, переключённый посреди отправки, может отправить сообщение от
  одного пресета с резюме от другого, а отозвать сообщение живому человеку нельзя.
  Если воркер не уложился в бюджет остановки, переключение **отклоняется** с настоящим
  состоянием, а не выполняется наполовину.
- **D10 — резюме: библиотека, пресет ссылается на одно.** Файлы загружаются один раз,
  пресеты ссылаются на нужный. Два пресета могут делить одно резюме; замена файла
  обновляет его для всех, кто на него ссылается.
- **D11 — резюме лежит в каталоге данных, а не в каталоге проекта.** Со стороны
  интерфейса разницы нет: кнопка «загрузить», файл выбирается, приложение им
  пользуется. Но каталог проекта — это git, и ровно так произошла исходная утечка: в
  закоммиченном архиве лежало резюме предыдущего автора с ФИО, телефоном и почтой.
  Файлы живут в `$JOB_MONITOR_DATA_DIR/resume/` с правами `0600`.
- **D12 — подстановки в шаблоне сообщения только надёжные.** `{канал}`,
  `{ключевое_слово}` (то, по которому пост совпал) и `{профессия}` из пресета. Пост в
  Telegram-канале — свободный текст без структуры, поля «название вакансии» в нём нет;
  любая эвристика по извлечению заголовка иногда даёт мусор, а мусор уходит живому
  человеку в личку.
- **D13 — защита сессий: права `0600` плюс вынос каталога данных из синхронизации.**
  Шифрование at rest отвергнуто: Keychain даёт защиту только от копирования файла, а
  пароль при каждом запуске ломает автозапуск и требует новой зависимости. Реальный
  вектор, который закрываем, — бэкап каталога данных в чужое облако.

## 4. Модель данных

### 4.1 Миграция 003 — три таблицы

```sql
CREATE TABLE presets (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT    NOT NULL UNIQUE,
    position   INTEGER NOT NULL,
    criteria   TEXT    NOT NULL,   -- JSON, валидируется SearchCriteria
    created_at TEXT    NOT NULL,
    updated_at TEXT    NOT NULL
);

CREATE TABLE resumes (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    original_name TEXT    NOT NULL,        -- что загрузил пользователь, только для показа
    stored_name   TEXT    NOT NULL UNIQUE, -- как лежит на диске, генерируем мы
    size_bytes    INTEGER NOT NULL,
    uploaded_at   TEXT    NOT NULL
);

CREATE TABLE tg_found (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    channel         TEXT    NOT NULL,
    message_id      INTEGER NOT NULL,
    found_at        TEXT    NOT NULL,
    username        TEXT,
    preview         TEXT,
    matched_keyword TEXT,
    UNIQUE (channel, message_id)
);
CREATE INDEX idx_tg_found_at ON tg_found(found_at);
```

`criteria` — JSON-документ, а не набор нормализованных таблиц. Критерии всегда читаются
целиком, на каждой итерации воркера, и никогда не ищутся SQL-запросом; шесть-семь
таблиц со join'ами на каждое чтение платили бы сложностью за запросы, которых в
продукте нет. Валидация живёт в pydantic, где она уже живёт для настроек.

`tg_found` заводится **на запись, без интерфейса и без статусов** — они в подпроекте 2.
Причина вытащить таблицу раньше: найденные-но-неотправленные посты сейчас не
сохраняются нигде, только событием в `worker_events`, поэтому до появления таблицы
каждая находка теряется безвозвратно и потом её не восстановить. Уникальность пары
`(channel, message_id)` заодно даёт дедупликацию постов, которой нет вовсе: один пост,
перечитанный на следующем круге, обрабатывается заново.

### 4.2 Разделение модели настроек

`AppSettings` распадается на две модели, обе с `extra="forbid"` на запись и терпимым
фильтром неизвестных ключей на чтение — как это уже сделано для настроек.

**`SearchCriteria`** — содержимое пресета:

| Поле | Смысл |
|------|-------|
| `channels` | Telegram-каналы |
| `professions` | названия профессий: поисковые запросы hh.ru и подстановка `{профессия}` |
| `tg_keywords` | по чему ловить посты в Telegram |
| `tg_exclude` | стоп-слова для Telegram |
| `hh_exclude` | стоп-слова для hh.ru |
| `hh_salary_from` | зарплата от |
| `hh_experience` | одно значение из набора опыта |
| `hh_employment` | несколько значений из набора занятости |
| `hh_schedule` | несколько значений из набора графика |
| `hh_search_period` | глубина поиска в днях |
| `template` | шаблон сообщения в Telegram |
| `hh_cover_letter` | сопроводительное письмо на hh.ru |
| `hh_resume_id` | идентификатор резюме **на стороне hh.ru** |
| `resume_id` | ссылка на запись в нашей таблице `resumes`, может быть пустой |

Если `resume_id` пуст, TG-воркер отправляет сообщение **без вложения**, а не
отказывается работать: резюме — не обязательная часть отклика, и человек вправе
писать только текстом. Отсутствие резюме интерфейс показывает явно, чтобы это не
выяснялось из логов.

**`GlobalSettings`** — остаётся в таблице `settings`: `delay_min`, `delay_max`,
`max_per_day`, `history_limit`, `safe_mode`, `parse_history`, `tg_autostart`,
`hh_max_per_day`, `hh_delay_min`, `hh_delay_max`, `hh_check_interval`, `hh_autostart`,
`hh_selenium_steps`, `active_preset_id`.

**Константы, не настройки:** `HH_AREA_ID = 113` в одном названном месте;
`HH_EXPERIENCE` (`noExperience` — нет опыта, `between1And3` — от 1 до 3 лет,
`between3And6` — от 3 до 6 лет, `moreThan6` — более 6 лет); `HH_EMPLOYMENT` (`full` —
полная, `part` — частичная, `project` — проектная, `probation` — стажировка,
`volunteer` — волонтёрство); `HH_SCHEDULE` (`remote` — удалённо, `fullDay` — полный
день, `flexible` — гибкий, `shift` — сменный).

Занятость и график — множественный выбор, а не переключатель одного значения: hh.ru
принимает несколько, и одно значение сужает выдачу, отсекая вакансии, помеченные
сразу двумя типами. Опыт — одно значение, как на самом hh.ru.

**Что уезжает из модели:** `file_path` (недостижимое из интерфейса поле, дефект L14)
заменяется на `resume_id`; `hh_area_ids` становится константой; `hh_keywords` сливается
с `professions`; `keywords` и `exclude` переименовываются в `tg_keywords` и
`tg_exclude`, чтобы сторона была видна из имени.

### 4.3 Перенос существующих настроек

Миграция читает текущую строку настроек и собирает из неё пресет
«Импортированные настройки», делает его активным и убирает перенесённые ключи из
`settings`. Если `file_path` указывает на существующий файл — он копируется в библиотеку
резюме и привязывается к пресету; если файла нет, поле резюме остаётся пустым, и
интерфейс это показывает.

Миграция идемпотентна: повторный прогон не создаёт второй пресет и не теряет данные.

**Перед миграцией приложение копирует файл БД** в `job_monitor.db.bak-003`. Это
единственный необратимый шаг подпроекта, и он трогает единственную таблицу, где лежат
реальные настройки пользователя; копия стоит одну строку и закрывает класс отказа
«миграция прошла наполовину, восстанавливать нечего».

### 4.4 Значения по умолчанию

Чистая установка получает один пресет «Мой поиск» **со всеми списками пустыми**. Ни
одного чужого канала, ключевого слова или стоп-слова в коде не остаётся.

## 5. API

### 5.1 Пресеты

| Метод | Путь | Что делает |
|-------|------|------------|
| `GET` | `/api/presets` | список: `id`, `name`, `position`, активен ли, сводка (сколько каналов и профессий, имя резюме) |
| `POST` | `/api/presets` | создать; принимает `name` и необязательный `copy_from` |
| `GET` | `/api/presets/{id}` | полные критерии |
| `PATCH` | `/api/presets/{id}` | частичное обновление критериев: слияние с сохранённым, затем валидация целого |
| `DELETE` | `/api/presets/{id}` | удалить |
| `POST` | `/api/presets/{id}/activate` | переключиться |

`position` присваивается при создании как максимум существующих плюс один; порядок
меняется отдельным `PATCH` и определяет порядок кнопок в интерфейсе. Имя пресета
уникально: переименование в уже занятое имя отдаёт 400, а не создаёт двойника.

**Запреты на удаление**, оба чтобы не получить молча нерабочее состояние: нельзя
удалить активный пресет и нельзя удалить последний. Оба отдают 400 с объяснением.

**Активация** гасит работающих воркеров, меняет `active_preset_id` и возвращает, что
именно остановлено: `{"activated": <id>, "stopped": ["tg", "hh"]}`. Если воркер не
уложился в бюджет остановки — активация отклоняется с настоящим состоянием воркера
(D9).

### 5.2 Библиотека резюме

| Метод | Путь | Что делает |
|-------|------|------------|
| `POST` | `/api/resumes` | загрузка файла (multipart) |
| `GET` | `/api/resumes` | список |
| `GET` | `/api/resumes/{id}/download` | скачать — проверить, то ли загрузили |
| `DELETE` | `/api/resumes/{id}` | удалить |

Удаление отклоняется, если на файл ссылается хотя бы один пресет, и ответ перечисляет
какие: молчаливая поломка чужого пресета хуже отказа.

**Загрузка — новая поверхность атаки, поэтому требования жёсткие:**

- белый список расширений: `.pdf`, `.doc`, `.docx`, `.rtf`, `.odt`, `.txt`;
- ограничение размера — 10 МБ;
- **имя файла от клиента никогда не становится путём.** Имя на диске генерируем мы
  (`<id>.<расширение>`), клиентское храним в `original_name` только для показа и
  экранируем при отрисовке;
- проверка, что итоговый путь лежит внутри каталога резюме — защита от `../` и
  абсолютных путей в имени;
- права готового файла `0600`, каталога `0700`;
- запись атомарна: временный файл в том же каталоге, затем `os.replace`, как уже
  сделано для `.env`.

### 5.3 Глобальные настройки

`/api/config` остаётся, но отдаёт только глобальное плюс `active_preset_id`. Критерии
уходят в `/api/presets/{id}`.

### 5.4 Отказ старта при пустых критериях

`POST /api/tg/start` отдаёт 400 «в пресете „Мой поиск“ нет каналов» или «нет ключевых
слов»; `POST /api/hh/start` — «нет профессий». Сейчас воркер в такой ситуации просто
крутится и ничего не находит, и понять почему нельзя.

## 6. Поведение воркеров

Воркеры читают активный пресет на каждой итерации — там, где сейчас читают настройки.
Отдельного механизма перезагрузки не нужно.

Лимиты в сутки и дедупликация остаются глобальными (D7): отправка, сделанная из пресета
A, видна пресету B. Написать одному человеку дважды из разных пресетов нельзя.

## 7. Каталог данных и синхронизация

При первом запуске — попытка `tmutil addexclusion` для каталога данных: macOS-only, не
фатально, отказ пишется в лог. Ужесточение защиты — best-effort, а не условие запуска;
это уже установленное в проекте правило (`job_monitor/paths.py::tighten`).

Плюс предупреждение в интерфейсе, если путь каталога данных выглядит как внутри iCloud
Drive, Dropbox, Google Drive или OneDrive. Это реальный риск именно тогда, когда
пользователь сам задал `$JOB_MONITOR_DATA_DIR`: файл сессии Telethon содержит
`auth_key`, которого достаточно для входа в аккаунт в обход 2FA, и попадание каталога в
чужое облако сводит на нет права `0600`.

`SECURITY.md` получает абзац об этом.

## 8. Минимальная адаптация текущего интерфейса

Подпроект 1 меняет контракт API, а интерфейс переписывается только в подпроекте 3.
Поэтому подпроект 1 обязан оставить приложение работоспособным: переключатель пресетов,
загрузка резюме вместо мёртвого пикера, и правка тех мест, которые читали ушедшие поля.
Это поддержание работоспособности, а не редизайн: у проекта жёсткое правило, что ни
одна задача не оставляет его в нерабочем состоянии.

## 9. Что закрепляем тестами

Мутационный аудит предыдущей ветки показал, что вакуумных тестов в наборе нет, зато
были инварианты, объявленные в коде и не закреплённые ничем — включая allow-лист CORS,
расширение которого проходило при полностью зелёном наборе. Поэтому список ниже —
часть спецификации, а не деталь реализации.

- **Хардкода нет**: тест падает, если в значениях по умолчанию появится непустой список
  поисковых критериев.
- **Загрузка файла**: имя с `../` отвергнуто; расширение вне белого списка отвергнуто;
  размер сверх лимита отвергнут; клиентское имя не стало путём; права готового файла
  `0600`.
- **Отказ старта при пустых критериях** — поведенчески, вызовом роута, а не проверкой
  существования функции.
- **Переключение атомарно**, критерии одного пресета не протекают в другой.
- **Удаление активного и последнего пресета** отклоняется.
- **Дедупликация и лимиты глобальные**: отправка из пресета A видна пресету B.
- **`tg_found`**: уникальность пары канал+сообщение действительно дедуплицирует.
- **Миграция 003** идемпотентна, переносит существующие настройки без потерь, делает
  копию БД перед работой.

Каждый новый тест обязан быть дискриминирующим: для него формулируется мутация, которая
должна его свалить, и эта мутация прогоняется.

## 10. Глобальные ограничения (наследуются)

- Python `>=3.11`, проверка на 3.13.3; зависимости закреплены в `requirements.lock`.
- Запрещены `eval`, `exec`, `pickle`, `marshal`, `shell=True`, установка пакетов в
  рантайме.
- Ни один секрет не попадает в БД, в ответы API, в логи и в репозиторий.
- Никакое состояние не резолвится относительно каталога репозитория — только через
  `job_monitor/paths.py`.
- Сервер слушает только `127.0.0.1`.
- Весь новый код с аннотациями типов. Обработчики `api/` обязаны объявлять
  возвращаемый тип — и осторожно: в FastAPI аннотация возврата становится
  `response_model`, то есть включает валидацию ответа, а аннотация наследником
  `Response` наоборот заставляет FastAPI не строить `response_model` вовсе, молча
  снимая валидацию.
- Тесты не ходят в сеть и не открывают браузер; прогон не создаёт ничего в домашнем
  каталоге и не зависит от порядка.
- `make test` зелёный на каждом коммите.

## 11. Открытые вопросы вне области подпроекта

- **CI отсутствует.** В репозитории нет ни одного workflow, поэтому набор тестов
  (461 на `master`, 507 на неслитой ветке `refactor/drop-cors-and-worker-epoch`)
  защищает только того, кто помнит запускать их локально; слияние предыдущей ветки
  приходилось гейтить вручную. Один workflow на `pytest` при push и pull request
  превратил бы набор из документа в работающую защиту.
- Часовой пояс: «отправок за сутки» считается по локальной дате машины. На машине в UTC
  или при переезде сутки съезжают. Кандидат в подпроект 2, где появляются статусы и
  даты становятся видны пользователю.
