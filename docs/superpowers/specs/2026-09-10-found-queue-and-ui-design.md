# Job Monitor: очередь найденного и переработка интерфейса

**Дата:** 2026-09-10
**Статус:** принята
**Подпроект:** 2 из 3 продуктовой переработки (вобрал в себя подпроект 3)
**Предшествующие:** `2026-09-08-hardening-and-rework-spec.md` (укрепление, закрыт),
`2026-09-09-presets-and-resume-library-design.md` (пресеты и резюме, закрыт)

## 1. Зачем это

Приложение умеет искать и откликаться само, но не умеет **показать найденное и
дать откликнуться вручную**. Между «робот нашёл» и «я решил» нет ничего:
hh-воркер кликает «Откликнуться» раньше, чем человек увидит вакансию, а
найденное в Telegram нигде не показывается.

Вторая половина — интерфейс. Он нарезан по типу сущности (каналы, ключевые
слова, шаблон, настройки, логи), и каждая страница внутри делится пополам на
Telegram и hh.ru. Отсюда повторы, измеренные по разметке: упоминаний hh — 21 на
дашборде, 40 в настройках, 6 в шаблоне, 5 в логах, плюс шесть разделителей
«TG / HH». Страница настроек — 205 строк и 13 карточек.

Подпроекты 2 и 3 объединены в один: очередь добавляет новый экран, а
переработка навигации немедленно его перестроила бы — экран пришлось бы делать
дважды.

## 2. Что обнаружилось при чтении кода

Три факта, найденные при подготовке спецификации; каждый меняет объём работ.

**Безопасного режима у hh.ru нет вообще.** `safe_mode` читает только
TG-воркер; `job_monitor/workers/hh.py` не обращается к нему ни разу. То есть
режима «найти и не откликаться» для hh не существует, и без него ручной отклик
невозможен по построению.

**Найденная вакансия попадает в базу только после обработки.**
`_process_one` вызывает `repo.upsert` после попытки отклика; найденное, но не
обработанное, не хранится нигде. Очередь была бы пуста.

**Колонка `tg_found.username` всегда пуста.** В подпроекте 1 таблица заводилась
на запись, и контакт был не нужен: `process_post` передаёт туда `None`. Для
очереди он нужен — иначе непонятно, кому писать.

**Настройки смешивают то, что бэкенд уже разделил.** Семь карточек из
тринадцати — критерии поиска, принадлежащие пресету; остальные шесть — общие
настройки приложения. Плюс два мусорных места: карточка «Регион поиска»
предлагает выбор там, где теперь константа (решение D8), а «Авторизация чатов
(session_web)» названа по файлу сессии, которого в приложении больше нет
(дефект L8 закрыт в плане 3).

## 3. Принятые решения

- **D14 — два раздельных списка, а не один общий.** Вакансия hh.ru и пост в
  Telegram разной природы: у первой есть название, компания и зарплата, у
  второго — канал и контакт для лички. Общая форма записи вынудила бы половину
  полей держать пустыми.
- **D15 — три ручных статуса:** «новая», «откликнулся сам», «не подходит».
  Ручной отклик — **отдельный** статус от автоматического «отклик отправлен»:
  видно, что сделал робот, а что человек. Автоматические статусы («пропущено»,
  «ошибка сценария») остаются.
- **D16 — ручной отклик не расходует суточный лимит.** Решение партнёра.
  Следствие названо явно: можно отправить двадцать откликов руками, и воркер
  добавит свои двадцать пять сверху. Лимит защищает аккаунт от бана, и
  Telegram с hh.ru не различают, кто нажал кнопку, — но отметка задним числом
  не должна останавливать воркера на весь день.
- **D17 — один переключатель безопасного режима на оба воркера.** Существующий
  `safe_mode` начинает действовать и на hh.ru: оба ищут и складывают в
  очередь, ничего не отправляя. Одно состояние вместо двух, и название
  наконец соответствует смыслу.
- **D18 — статусы хранятся в существующих таблицах.** Ни отдельной таблицы
  статусов (каждое чтение списка стало бы join'ом, а состояние одной записи
  размазалось бы по двум таблицам), ни единой таблицы найденного (потребовала
  бы пересоздать `hh_applications` с реальной историей откликов — правило
  проекта запрещает).
- **D19 — дедупликация по решённости, а не по наличию строки.** Прямое
  следствие D18: если писать строку при находке, проверка «строка есть →
  пропустить» начнёт отбрасывать то, что воркер только что нашёл.
- **D20 — интерфейс нарезается по задаче, источник становится фильтром.**
  Четыре экрана: Обзор, Найдено, Отправлено, Настройки. Telegram и hh.ru
  перестают быть половинами каждой страницы.
- **D21 — критерии живут на «Обзоре», в настройках только общее.** Бэкенд уже
  разделил критерии и глобальные настройки; интерфейс приводится в
  соответствие.

## 4. Модель данных

### 4.1 Словарь статусов

Новый модуль `job_monitor/statuses.py` — один словарь на оба списка. Списки
раздельные (D14), но статусы общие: иначе «откликнулся сам» в Telegram и в
hh.ru стали бы разными строками и каждый счётчик пришлось бы писать дважды.

| Константа | Значение | Кто ставит |
|-----------|----------|------------|
| `NEW` | `новая` | робот при находке |
| `AUTO_APPLIED` | `отклик отправлен` | робот (совпадает с нынешним `HH_STATUS_APPLIED`) |
| `MANUAL_APPLIED` | `откликнулся сам` | человек |
| `DISMISSED` | `не подходит` | человек |
| `SKIPPED` | `пропущено` | робот |
| `SCENARIO_ERROR` | `ошибка сценария` | робот |

Плюс два множества:

- `DECIDED` — всё, кроме `NEW`. Это и есть новая дедупликация (D19).
  `SKIPPED` входит сюда намеренно: так ведёт себя нынешний код (`exists()`
  пропускает вакансию навсегда), и менять это заодно с переездом на статусы
  значило бы смешать два изменения в одном. Вернуть такую вакансию в работу
  можно вручную — см. раздел 7.
- `MANUAL` — `MANUAL_APPLIED` и `DISMISSED`; только их принимает API.

`HH_STATUS_APPLIED` и `HH_STATUS_SCENARIO_ERROR` переезжают в этот модуль;
прежние имена остаются алиасами, чтобы не править места использования разом.

### 4.2 Миграция 004

Только добавление колонок — таблицы не пересоздаются (правило
`db/migrations.py`):

```sql
ALTER TABLE tg_found ADD COLUMN status    TEXT NOT NULL DEFAULT 'новая';
ALTER TABLE tg_found ADD COLUMN status_at TEXT;
ALTER TABLE tg_found ADD COLUMN usernames TEXT;          -- JSON-массив
ALTER TABLE hh_applications ADD COLUMN status_source TEXT NOT NULL DEFAULT 'робот';

CREATE INDEX IF NOT EXISTS idx_tg_found_status ON tg_found(status);
CREATE INDEX IF NOT EXISTS idx_hh_status       ON hh_applications(status);
```

Существующие строки `hh_applications` получают источник «робот»: их все писал
он. Существующие строки `tg_found` остаются со статусом «новая» — знать, был ли
по ним отклик, неоткуда, а дедупликацию контактов это не трогает: она живёт в
`tg_contacts`.

Копия базы перед миграцией снимается существующим механизмом
(`_backup_before`, один раз за прогон, через sqlite3-backup).

### 4.3 Контакты в `tg_found`

`process_post` начинает писать в `usernames` список извлечённых из поста
контактов вместо нынешнего `None`. Гранулярность статуса — пост целиком, а не
отдельный контакт: пост это единица находки, и решение «не подходит»
принимается по вакансии, а не по человеку.

## 5. Поведение воркеров

**Безопасный режим у обоих (D17).** В `safe_mode` TG-воркер, как и сейчас,
находит и не отправляет; hh-воркер начинает вести себя так же — ищет,
записывает вакансию со статусом `NEW` и не кликает «Откликнуться».

**Запись при находке.** hh-воркер вызывает `upsert` со статусом `NEW` сразу
после разбора страницы поиска, до всякой попытки отклика. Это и наполняет
очередь.

**Дедупликация по решённости (D19).** В `_blocking_loop` проверка
`if repo.exists(vacancy_id): continue` заменяется на «статус в `DECIDED` →
пропустить». Статус `NEW` обработку не блокирует.

Это самое опасное место подпроекта: невнимательность здесь даёт не падение, а
тихую остановку автоматики — воркер отбрасывает то, что сам нашёл. Отдельный
шаг плана, отдельный поведенческий тест через настоящий цикл.

**Счётчики не трогаются.** `applied_on` считает строки со статусом
`AUTO_APPLIED`; ручной отклик получает другой статус и в счётчик не попадает —
D16 выполняется формой данных, а не отдельной проверкой.

## 6. Ручные статусы

**Telegram, «откликнулся сам».** Регистрирует все контакты поста через
`TgRepo.ensure_contact` — воркер больше никогда им не напишет
(`was_sent` смотрит в `tg_contacts`), а дневной счётчик не тронут, потому что
записи в `tg_sends` не создаётся. Метод написан для импорта старых данных и
подходит буквально: он существует ровно для случая «контакт известен, отправки
не было».

**Telegram, «не подходит».** Только статус: пост уже дедуплицирован парой
(канал, сообщение), контакты в `tg_contacts` не попадают — человек может
встретиться в другой вакансии, которая подойдёт.

**hh.ru, оба статуса.** Только статус в `hh_applications`; он попадает в
`DECIDED`, поэтому воркер вакансию больше не тронет.

## 7. API

| Метод | Путь | Что делает |
|-------|------|------------|
| `GET` | `/api/found/tg` | список найденного в Telegram; фильтр `status`, постраничность |
| `GET` | `/api/found/hh` | то же для hh.ru |
| `PATCH` | `/api/found/tg/{id}` | сменить статус |
| `PATCH` | `/api/found/hh/{vacancy_id}` | сменить статус |

**Ссылку строит бэкенд.** Для hh.ru она уже есть в `url`; для Telegram
собирается из канала и идентификатора сообщения (`https://t.me/<канал>/<id>`).
Фронтенду незачем знать формат чужих URL, а гвард схемы в `el()` остаётся
единственной точкой проверки.

**Руками ставится только ручной статус.** `PATCH` принимает значения из
`MANUAL` и отвергает `AUTO_APPLIED` с 400. Это слово робота: разрешить ставить
его руками — значит сделать счётчик «отправлено сегодня» неправдой.

**Возврат в `NEW` разрешён не из любого состояния.** Вернуть запись в очередь
можно из `DISMISSED` (передумал) и из `SKIPPED` (робот не смог — пусть
попробует снова). Из `AUTO_APPLIED` и `MANUAL_APPLIED` — **нельзя**: отклик
уже ушёл работодателю, а `NEW` означает «обработать», то есть воркер отправил
бы второй отклик на ту же вакансию. Для Telegram от этого защищает
дедупликация контактов, для hh.ru — ничто, поэтому запрет ставится на уровне
роута и закрепляется тестом.

Это место найдено самопроверкой спецификации: первая редакция разрешала
возврат в `NEW` из любого статуса, и получалось, что отметка «я передумал» на
уже отправленном отклике заставляет робота откликнуться повторно.

**Старый роут `GET /api/hh/vacancies` заменяется** на `/api/found/hh`;
единственный его потребитель — наш же фронтенд.

## 8. Интерфейс

**Четыре экрана** (D20): Обзор, Найдено, Отправлено, Настройки.

**Полоса состояния** поверх всех экранов: состояние каждого воркера,
безопасный режим — **словами** («собираю, не отправляю»), активный пресет.
Сейчас это разбросано по дашборду и настройкам, а смысл безопасного режима не
написан нигде: только галочка, до которой надо дойти и вспомнить, что она
значит.

**Обзор.** Три плитки метрик с переключателем источника вместо нынешних шести
с тремя повторяющимися подписями; кнопки запуска; пресеты; критерии активного
пресета (D21); последние действия.

**Найдено.** Две подвкладки по источнику. Строка: заголовок или превью,
метаданные, бейдж статуса, ссылка «открыть», кнопки «Откликнулся» и «Не
подходит». Фильтр по статусу: все, новые, решённые.

**Отправлено.** Переписка в Telegram (нынешняя вкладка «Чаты») и отправленные
отклики hh.ru.

**Настройки** — только общее, четырьмя группами: режим и лимиты; доступы
(ключи Telegram, вход в hh.ru); библиотека резюме; продвинутое (сценарий
Selenium).

**Мусор, исчезающий по дороге:** карточка «Регион поиска», карточка
«Авторизация чатов (session_web)» (переименовывается во «Вход в Telegram»),
дублирующиеся плитки метрик, шесть разделителей «TG / HH».

**Инварианты, которые обязаны уцелеть.** Ноль инлайновых `on*=` обработчиков в
разметке; ноль сборки HTML-строк в `app.js`; гвард схемы URL в `el()`; баннер
протухшего токена на 403; один периодический опрос `/api/state`; все сетевые
вызовы через помощники `apiGet`/`apiSend`/`apiUpload`. За них заплачено тремя
планами, и переписывание фронтенда — ровно та работа, в которой их теряют.

## 9. Долги подпроекта 1, забираемые сюда

Два замечания финального ревью того же класса «состояние разошлось с ответом»:

- **M-2:** `PATCH /api/presets/{id}` применяется наполовину — запрос с новым
  именем и негодным критерием возвращает 422, но имя уже сохранено. Клиент
  видит отказ и не знает, что переименование прошло.
- **M-3:** файл резюме пишется до вставки строки в базу; отказ вставки
  оставляет его в каталоге навсегда — в списке его нет, удалить из интерфейса
  нечем. Зеркально в удалении: файл стирается до строки.

## 10. Что закрепляется тестами

- воркер пропускает решённое и обрабатывает новое — поведенчески, через
  настоящий `_blocking_loop`;
- безопасный режим у **обоих** воркеров: очередь наполняется, наружу не уходит
  ничего;
- «откликнулся сам» в Telegram регистрирует контакты и **не трогает** дневной
  счётчик;
- ручной отклик на hh.ru не попадает в счётчик отправленного;
- `PATCH` отвергает попытку выставить `AUTO_APPLIED` руками;
- возврат в `NEW` из отправленного отклика отвергается, из `DISMISSED` и
  `SKIPPED` разрешён — иначе робот отправил бы второй отклик тому же
  работодателю;
- ссылка на пост Telegram собирается бэкендом и проходит гвард схемы;
- миграция 004 идемпотентна, делает копию базы, даёт существующим строкам
  осмысленные значения;
- инварианты фронтенда из раздела 8 — на каждом экране, а не один раз;
- отвергнутое сохранение нигде не показывается как успешное.

Каждый новый тест обязан быть дискриминирующим: для него формулируется
мутация, которая должна его свалить, и эта мутация прогоняется. Проверки,
держащиеся за счёт соседних, в этом проекте находились четырежды — при
написании тестов очереди это первое, что нужно проверять.

## 11. Вне области

Адаптивная вёрстка под узкие экраны (партнёр не выбрал; для инструмента на
`127.0.0.1` польза спорная). Горячие клавиши. Смена визуального стиля: цвета,
шрифты и карточки остаются, меняется структура и плотность. Политика хранения
истории (`tg_found`, `worker_events` растут неограниченно — признанный долг).
Остальные замечания ревью и аудита подпроекта 1 — разобраны отдельно
после подпроекта, см. `docs/superpowers/outstanding-findings.md`.

## 12. Глобальные ограничения (наследуются)

- Python `>=3.11`; зависимости закреплены в `requirements.lock`; новых
  зависимостей подпроект не добавляет.
- Запрещены `eval`, `exec`, `pickle`, `marshal`, `shell=True`, установка
  пакетов в рантайме.
- Ни один секрет не попадает в БД, в ответы API, в логи и в репозиторий.
- Состояние резолвится только через `job_monitor/paths.py`.
- Сервер слушает только `127.0.0.1`.
- Аннотации типов на новом коде; обработчики `api/` объявляют возвращаемый
  тип. Ловушка FastAPI: аннотация возврата становится `response_model`, а
  аннотация наследником `Response` наоборот отключает валидацию.
- Тесты не ходят в сеть, не открывают браузер, не пишут в домашний каталог и
  не зависят от порядка.
- `make test` зелёный на каждом коммите. На старте подпроекта — **662 passed**.
