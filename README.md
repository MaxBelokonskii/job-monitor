# 🤖 Job Monitor v2.1.0

![GUI](docs/images/v2.0(Dashboard).png)

> Автоматизированная система поиска вакансий и отправки откликов для Junior QA / стажёров  
> **Python · Telegram API · Selenium · FastAPI · Web UI**

---

## 📌 О проекте

Поиск первой работы в QA — это десятки каналов в Telegram и сотни вакансий на HH.ru. Вместо ручного мониторинга я автоматизировал весь процесс: система работает в фоне, находит подходящие вакансии и отправляет отклики быстрее, чем успеваешь прочитать объявление.

Проект начинался как простой Python-скрипт с bat-меню, вырос до полноценного веб-приложения с двумя модулями автоматизации, REST API и красивым интерфейсом.

## 🚀 Функциональность

### Telegram Monitor
- Мониторинг публичных каналов в реальном времени через **Telethon MTProto API**
- Умная фильтрация по ключевым словам и исключениям (junior/intern/стажировка vs senior/lead)
- Автоматическая отправка сообщения + PDF резюме найденным контактам
- Дедупликация между запусками — в SQLite (`job_monitor.db`, таблицы
  `tg_contacts`/`tg_sends`), а не в текстовом файле: одному контакту не
  напишут дважды даже после перезапуска
- Лимит откликов в день (защита от бана); лимит перечитывается из БД на
  каждой итерации, поэтому смена суток обрабатывается сама собой
- `SAFE_MODE` — тестовый режим без реальной отправки
- Парсинг истории каналов при старте
- Обработка `FloodWaitError` с автопаузой

### HH.ru Monitor
- Автоматический поиск вакансий через **Selenium + Chrome**
- Фильтры: регион, опыт, зарплата, график, период публикации
- Автоматический отклик с сопроводительным письмом
- Сохранение сессии через cookies (повторный вход не нужен)
- Вход в hh.ru прямо из UI — вкладка «Вход в hh.ru», неблокирующая
  (см. раздел «Вход в hh.ru» ниже)
- Редактор сценария автокликания прямо в UI — сценарий действительно
  исполняется воркером по белому списку шагов (`job_monitor/workers/hh_steps.py`)

### Web Interface
- Единый дашборд для TG и HH с метриками
- Управление каналами, ключевыми словами, шаблонами
- Просмотр переписки с контактами прямо в браузере (Telegram чаты)
- Раздельные логи TG и HH с цветовой подсветкой (`logs/tg_system.log` и
  `logs/hh.log` в каталоге данных, с ротацией по размеру)
- Автозапуск воркеров при старте приложения

## ⚙️ Установка и запуск

### 1. Клонировать репозиторий
```bash
git clone https://github.com/MaxBelokonskii/job-monitor.git
cd job-monitor
```

Первому клону нужен доступ в сеть: `make install` скачивает зависимости
(версии зафиксированы в `requirements.lock`, но сами пакеты всё равно
приходят из PyPI), а сборка pre-commit хука (`detect-secrets`) при первом
коммите отдельно скачивает свою среду.

### 2. Установить и запустить

**macOS/Linux:**
```bash
make install   # создаёт .venv, ставит зависимости из pyproject.toml + requirements.lock
make run       # uvicorn api.main:app --host 127.0.0.1 --port 8000
```

То же самое делает установленная команда `job-monitor run [--host] [--port]`.
Один процесс поднимает всё: веб-интерфейс, API и оба воркера. Запускать
второй экземпляр на том же каталоге данных нельзя — БД и сессия Telethon одни
на каталог.

**Windows** — двойной клик по `start_web.bat`: при первом запуске он создаёт
`.venv` рядом с проектом и ставит зависимости внутрь него из
`requirements.lock`, дальше просто поднимает сервер — ни системный Python, ни
абсолютные пути интерпретатора не используются. Установка на каждом запуске
не повторяется: обычный старт не требует сети. Признак «уже установлено» —
файл `.venv\.install-ok`, который появляется только после успешной установки:
если она сорвалась, следующий запуск повторит её сам, а не сделает вид, что
всё готово. Переустановить зависимости принудительно (например после
обновления `requirements.lock`) — `start_web.bat setup` из командной строки.

В обоих случаях сервер поднимется на `http://127.0.0.1:8000`, и это
единственный адрес, который он слушает.

### 3. Настроить окружение

При первом запуске приложение создаёт каталог данных `~/.job-monitor` (права
`0700`) и файл `.env` в нём (права `0600`) — задавать `TG_API_ID` и
`TG_API_HASH` можно прямо через веб-интерфейс, без ручного редактирования
файлов. Файл `.env.example` в репозитории — только справочный шаблон того,
какие переменные существуют. Кроме этих двух ключей в `.env` ничего не
живёт: `safe_mode`, `parse_history`, `history_limit` и остальные
прикладные настройки хранятся в `job_monitor.db` и правятся через UI —
менять их в `.env` бессмысленно, приложение их оттуда не читает. Если вы
обновились с версии, которая писала туда `SAFE_MODE`, `PARSE_HISTORY` или
`HISTORY_LIMIT`, при первом же сохранении ключей эти строки будут удалены —
чтобы `SAFE_MODE=false` в файле не выглядел действующей настройкой. Всё
остальное, что вы дописали в `.env` сами, приложение не трогает.

Каталог данных переопределяется переменной окружения
`JOB_MONITOR_DATA_DIR` — например, чтобы держать несколько независимых
профилей или вынести состояние на другой диск:
```bash
# macOS/Linux
export JOB_MONITOR_DATA_DIR=/path/to/data
```
```bat
:: Windows
set "JOB_MONITOR_DATA_DIR=D:\job-monitor-data"
```
Если переменная не задана, используется `~/.job-monitor`. Единственное
место, где вычисляется этот путь — `job_monitor/paths.py`.

В каталоге данных приложение держит всё своё состояние:

| Путь | Что это |
|------|---------|
| `.env` | только `TG_API_ID` и `TG_API_HASH` (права `0600`); прикладные настройки живут в базе |
| `job_monitor.db` | SQLite: настройки, контакты, отправки, вакансии, события воркеров |
| `telegram.session` | сессия Telethon — одна на всё приложение (и воркер, и веб-чат) |
| `hh_cookies.json` | cookies сессии hh.ru (права `0600`) |
| `logs/tg_system.log` | лог TG-стороны — вкладка «Логи TG» в UI |
| `logs/hh.log` | лог HH-стороны — вкладка «Логи HH» в UI |

Логи пишет `job_monitor/logging_setup.py`: обработчики подключаются в
`lifespan` приложения, файлы создаются с правами `0600` и ротируются по
размеру (`RotatingFileHandler`), поэтому расти без границ не могут. PID-файлов
(`monitor_pid.txt`, `hh_pid.txt`) больше нет: воркеры живут внутри процесса, и
их состояние отдаёт `GET /api/state`.

Подробно о том, что где хранится, какими механизмами это защищено и что
делать при утечке секрета — в [`SECURITY.md`](SECURITY.md).

### 4. Вход в hh.ru

hh.ru не даёт API для откликов, поэтому вход выполняется руками в настоящем
окне Chrome, а приложение потом переиспользует cookies. Раньше это делал
`hh_monitor.py`, останавливаясь на `input()` в консоли — а запущенный из UI
как подпроцесс без stdin он просто зависал, и hh-сценарий не работал вообще
(дефект L4). Теперь это неблокирующая машина состояний: приложение не ждёт
ввода, оно хранит состояние и отвечает на два вызова.

Карточка «Вход в hh.ru» на вкладке HH:

1. **«Открыть вход в hh.ru»** (`POST /api/hh/login/start`) — открывается окно
   Chrome на странице входа. Состояние → `browser_open`.
2. Войдите в окне сами: пароль, код из письма, капча — что попросят.
3. **«Я вошёл, сохранить сессию»** (`POST /api/hh/login/confirm`) — приложение
   проверяет, что вход действительно состоялся, сохраняет cookies в
   `hh_cookies.json` (права `0600`) и закрывает окно. Состояние → `logged_in`.
   Если вход ещё не завершён, состояние не меняется и UI скажет об этом —
   можно дожать вход и нажать кнопку снова.

Текущее состояние (`logged_out` / `browser_open` / `logged_in`) видно в
карточке и приходит в `GET /api/state`. Пока cookies живы, повторный вход не
нужен: воркер подхватит их сам.

### 5. Обновление с предыдущей версии

Версия до `2.1.0` хранила состояние прямо в каталоге репозитория. Эта
версия читает и пишет настройки (каналы, ключевые слова, шаблоны, лимиты)
через SQLite под `$JOB_MONITOR_DATA_DIR` (по умолчанию `~/.job-monitor`,
файл `job_monitor.db`) — если просто обновить код на месте, ничего не
перенеся, настройки откатятся на значения по умолчанию, `all_sent_users.txt`
и `hh_sent.json` не будут найдены (и монитор напишет заново всем, кому уже
писал раньше — риск бана в Telegram), а Telethon-сессия не найдётся и
потребует повторного входа по коду.

**Порядок важен: сначала `migrate-legacy`, потом перенос файлов вручную.**
Команда `migrate-legacy` читает `config.json`, `logs/sent_log_*.txt`,
`all_sent_users.txt` и `hh_sent.json` из старого клона и переносит
настройки, контакты и историю вакансий в SQLite — не трогая `.env` и
Telethon-сессии. Если старый клон — это тот же каталог, что вы сейчас
обновляете (типичный случай `git pull` на месте), достаточно команды из
`Makefile`, которая по умолчанию смотрит в текущий каталог (`--from .`):

```bash
make install          # если ещё не делали — обновит зависимости
make migrate-legacy   # job-monitor migrate-legacy --from .
```

Если старый клон лежит в другом месте, укажите путь явно:

```bash
.venv/bin/python -m job_monitor.cli migrate-legacy --from /путь/к/старому/клону
```

Команда сама создаёт `$JOB_MONITOR_DATA_DIR` при необходимости и печатает,
сколько настроек/контактов/отправок/вакансий перенесено и что пропущено
(например, секреты из `config.json` — они никогда не переносятся, секреты
живут только в `.env`). Повторный запуск безопасен для контактов и
вакансий; настройки, если они уже были перенесены (или изменены через UI),
второй раз не перезаписываются — команда сообщит об этом в списке
«пропущено».

Только теперь перенесите вручную то, что `migrate-legacy` не переносит —
секреты и живые Telethon-сессии, из корня старого клона:

```bash
mkdir -p ~/.job-monitor
mv .env             ~/.job-monitor/.env
mv session.session  ~/.job-monitor/telegram.session
```

Второй файл сессии, `session_web.session`, переносить не нужно: приложение
работает с одним клиентом Telethon и одной сессией `telegram.session` (дефект
L8 — два независимых логина в один аккаунт). Старый файл лучше удалить, он
содержит `auth_key`; подробности — в [`SECURITY.md`](SECURITY.md).

`config.json` в этот список не входит: начиная с этой версии его не
читает ни настройка, ни воркер — переносить нечего, а сам файл после
`migrate-legacy` можно просто оставить или удалить. Если вы
переопределяете каталог данных через `JOB_MONITOR_DATA_DIR`, подставьте
его значение вместо `~/.job-monitor` во всех командах выше.

**Перенесённые таблицы теперь и есть источник правды.** Воркеры пишут
отправки, вакансии и события прямо в `job_monitor.db`; `all_sent_users.txt`,
`sent_log_*.txt` и `hh_sent.json` не читает и не пишет больше никто. После
удачного `migrate-legacy` эти файлы можно удалить — но сначала убедитесь по
UI, что контакты и вакансии на месте: удалять их «на всякий случай» до
проверки не стоит, повторно импортировать будет уже неоткуда.

Кроме `run` и `migrate-legacy`, других команд у `job-monitor` нет:
`job-monitor run [--host] [--port]` поднимает веб-приложение (то же самое
делает `make run`); `--host` кроме `127.0.0.1` не принимается — это
проверяется до запуска uvicorn.

## 🧪 Тестирование и найденные баги

Прогон — `make test` (или `.venv/bin/python -m pytest -q`). Сети он не
требует и ничего не пишет в домашний каталог.

**Для полного прогона нужен Node.js.** `frontend/app.js` — не собираемый
скрипт, и единственный способ проверить его ПОВЕДЕНИЕ, а не наличие
подстроки, — исполнить настоящую функцию в `node`. Без него 14 тестов
пропускаются, и среди них поведенческие пины XSS и CSP: на такой машине
защита фронтенда держится только грепом по исходнику. Прогон об этом
предупреждает отдельной строкой, а не молча.

В процессе разработки я применял QA-подход к собственному проекту:

### Критические баги (найдены и исправлены)

| # | Баг | Причина | Фикс |
|---|---|---|---|
| 1 | Повторная отправка сообщений после перезапуска | Дневной лог сбрасывался, `sent_users` очищался | Добавлен постоянный `all_sent_users.txt` |
| 2 | Превышение лимита (35 вместо 25) | Лимит проверялся до цикла, но не внутри при multiple usernames | Проверка добавлена внутрь цикла по username |
| 3 | Конфликт Telegram сессий | `monitor.py` и `app.py` использовали одну сессию | Разделены на `telegram.session` и `telegram_web.session` |
| 4 | `Too many requests` без паузы | `FloodWaitError` игнорировался, скрипт продолжал слать | Добавлена обработка с `e.seconds` паузой |
| 5 | `ModuleNotFoundError: api` | uvicorn запускался не из директории проекта | Добавлен `cd /d "%BASE%"` в батник |
| 6 | JS `SyntaxError` из-за двойного экранирования | Regex в JS патчился через Python `str.replace` | Пересборка файла с нуля |
| 7 | Дублирование каналов в конфиге | Не было проверки при добавлении | Добавлена валидация на дубли |
| 8 | PID-файл не удалялся после краша | `atexit` не срабатывал при `SIGKILL` | `is_running()` чистит мёртвый PID-файл |

> Это история версий до `2.1.0`, и два пункта в ней с тех пор пересмотрены.
> №3 (две сессии Telegram) оказался не решением, а дефектом: два файла сессии
> — это два независимых логина в один аккаунт, сейчас сессия одна
> (`telegram.session`). №8 закрыт целиком: PID-файлов больше нет, воркеры —
> asyncio-таски под супервизором в том же процессе, см.
> `docs/adr/0001-in-process-workers.md`.

### Логические проблемы (найдены и исправлены)

- `api_hash` сохранялся в `config.json` открытым текстом → вынесен только в `.env`
- `load_config()` вызывался в цикле при каждом сообщении → кеш с TTL 30 сек
- `get_sent_list()` вызывал `load_config()` на каждую строку лога → вынесен за цикл
- Хардкод фильтра `["junior", "стаж", "intern"]` дублировал `keywords` из конфига → убран
- `system.log` рос бесконечно → добавлена ротация (обрезка до 5000 строк;
  сейчас границу держит `RotatingFileHandler` по размеру файла)
- CORS `allow_origins=["*"]` → ограничен до localhost

### Тест-кейсы (SAFE_MODE)

```
TC-001: Скрипт находит вакансию с ключевым словом "junior"
TC-002: Скрипт не откликается на вакансию с "senior" в тексте  
TC-003: Скрипт пропускает @bot аккаунты
TC-004: Повторная отправка одному контакту исключена
TC-005: При достижении лимита скрипт останавливается
TC-006: При FloodWaitError скрипт делает паузу и продолжает
```
